## Answers to the eight audit questions

1. **Coordinator:** no production LocalIntentPlan, IntentPlan, UndoIntent, IntentCommitSegment or HistoryGroup implementation/caller was found in runtime/apps. Name searches are corroboration, not proof alone: the actual HistorySubmitPort implementations were traced. CanvasEditingRuntime is the only production owner. Its span submit rejects `operations.size()!=1` and sources other than UndoRedo before its apply loop. Public facade/control paths do not supply a heterogeneous coherent-intent command. CanvasInteractionCoordinator/RuntimeComposition handle input/control ownership; they are not multi-op commit coordinators. Section uses one opcode17/18 operation, not a HistoryGroup.
2. **Preflight:** OperationEngine::prepare/admitPlan validate one operation against current state and build its StagedObjectView. prepareUndoableCommand validates the real inverse against that staged poststate and checks restored preimage/footprint. No owner preflights an ordered sequence on staged S0→S1→S2 before first canonical apply. Multi-operation span refusal is safe unavailability, not staged-sequence support.
3. **Reservation:** EditorHistory::HistoryCommandAdmission::admit calls prepareUndoableCommand, then prepareValidatedRecord reserves entries and retains real F/U/before/after before one admitted apply. Real forward/inverse payload measurement is in undoable_command.cpp. applyLocalHistoryOperation prepares one legacy entry before apply. Brush/eraser paths also contain post-apply record calls and are not evidence for the admitted-cohort guarantee. No group-wide history/preimage/outcome reservation exists. Existing allocation tests exercise the real Engine+History with a custom submit fixture; they do not exercise production Scene/event/receipt publication.
4. **Failure at N:** the real span port admits no two-operation batch, so no permitted forward item N is reachable there. A deliberately labeled negative control sequences ordinary real commands: rejection at item0 leaves everything unchanged; rejection at item1 leaves the first command's canonical projection, generation, Scene, event and History entry. This loop is NOT a production coordinator and is not an automatic-compensation test.
5. **Compensation and visibility:** ordinary Undo restores the captured Document projection, Scene world bounds and spatial-query IDs, but creates a new generation/stamp/event and retains the existing History entry with redo. Ten existing Scene publication checkpoints were injected on real admitted commands; committed canonical and History remain, Scene/RuntimeScene stay coherent and recovery reaches the current generation. This proves individual-operation publication/recovery, not failed-intent containment. A separate postcommit allocation probe found the receipt-copy failure below.
6. **One Undo:** two independent heterogeneous commands create two History entries; one Undo undoes only the latter. One SetTransforms batch or one PatchProperties batch over two targets creates one History unit; changing selection to a third object before Undo does not retarget it.
7. **Evidence kinds:** editor_history_test.cpp uses a fake submit port and call/payload assertions: UNIT only. FC08 history/allocation fixtures use the real Semantic engine and EditorHistory with a custom test submit owner: COMPONENT INTEGRATION, no production Scene. New audit tests use actual RuntimeComposition, CanvasEditingRuntime, EditorHistory, Scene/index and read-only real LocalOperationSink observations with existing test access seams: REAL-OWNER INTEGRATION. There is no end-to-end multi-intent producer to invoke; none is invented in tests.
8. **Crash/client scope:** no cross-client/crash atomicity is required or claimed. Intermediate per-operation events are allowed. Compensation must not erase committed metadata or conceal already observable prefix events.

## Executed failure probes

- Missing-entry RED: the available real Runtime span port rejects two valid forward candidates; no alternative production coordinator was found. This is a gap probe, NOT a request to remove its guard.
- Naive-fallback RED: two individually accepted operations followed by one Undo do not restore the original records. This counterexample is NOT a future conformance test for a new coordinator; that must bind a real accepted entry when one exists.
- Scene OOM probe: when the retained result fits existing capacity, the first postcommit allocation fails in derived publication. Command remains accepted with History1; generation advances1→2 while Scene initially remains1, and recovery reaches2. The initial copy-allocation hypothesis is not generalized from this passing scenario.
- **Receipt-growth OOM RED:** one existing Shape is followed by one real InsertObjects of two Shapes. The first C++ allocation after canonical generation advances fails while the new ChangeSet needs a larger retained result copy. Raw trace: `generation=2 ordinal=2 objects=3 history=0 scene=1`, then `TERMINATE_REACHED`. The isolated observer terminate handler exits86 without OS dialog; it does not recover or modify production behavior. Source chain is OperationEngine commit → submitAdmitted → noexcept observeApplied → lastAppliedCommit_ copy, before commitPrepared/publishAdmitted. This is a real controlled allocation failure, not a manually fabricated event trace. It establishes a postcommit fatal boundary and missing successful History/outcome finalization; it does not establish persistent recovery behavior or demand crash rollback.

The latter finding was missed by component allocation fixtures because their custom submit owner calls Engine directly, omitting CanvasEditingRuntime::observeApplied. Its unique detection value is exercising the real production postcommit receipt path after state has mutated. Classify/repair this owning layer separately before claiming graceful D07 receipt-failure containment. No product fix is included here.
