# SDK-01 host and SDK composition identity — candidate

This is a concrete proposal for review, not an implemented SDK or an accepted public API. Current Windows `windows_main.cpp` and Web `web_debug_ui.inl` obtain the mutable multi-selection port from their **host-owned** `RuntimeComposition`. A separately created `canvas_runtime_create` instance would own a different composition. Sending Debug UI controls to that second instance would be a silent data-loss/incorrect-target bug even if its ABI and unit tests passed.

Proposed integration uses a private, non-installed C++ bridge that registers the existing host-owned composition and its actual bound view in the SDK handle adapter. It produces ordinary typed C handle values for that exact owner, not a `RuntimeComposition*` passed through C or a second editor. The production host remains the lifecycle owner; the bridge holds no longer-lived ownership, is created only on the owner thread, invalidates all associated handles and drains/cancels pending adapter work before the host closes, and is inaccessible to ordinary SDK consumers. The existing platform host still owns its surface/input/render adapters in SDK-01. SDK-owned instances created through public `canvas_runtime_create` own their composition and use the same adapter implementation. No borrowed composition can outlive its host or be destroyed by the SDK bridge.

Migrate Windows and Web Debug UI to call the public selection API using these registered view handles. During transition, do not use the old mutable port for product submissions; do not delete its accessor until both migrated hosts pass equivalent behavior. A separate test-only observer may inspect the same owner's canonical state and History; it never submits the product action and is not installed as public API. Cross-runtime or cross-view handles, rebinds and released host handles must fail without mutation. Both host and SDK runtime instance/binding identities must be compared in tests, including after close/recreate. External installed clients test the owning `canvas_runtime_create` path, while Windows/Chrome host tests exercise the borrowed internal bridge. Test-only observer identity, actual product client path and canonical hashes must all refer to the same owner.

This proposal requires precise ownership, callback/close ordering, handle-table capacity/generation exhaustion, SDK instance/client ID mapping, source files and Windows/Chrome driver decisions to be bound before P32. In particular, V1 document/view calls contain only a 32-bit typed handle and no parent argument; an adapter must prevent cross-runtime/domain aliasing, stale slot reuse and generation wrap rather than relying only on a per-runtime table lookup. A nonzero 128-bit `CanvasClientId` cannot be truncated to the owner's uint64 client; use a bounded collision-free instance-local mapping and return explicit capacity failure. No generic platform frame or physical-presentation claim follows from this host bridge.
