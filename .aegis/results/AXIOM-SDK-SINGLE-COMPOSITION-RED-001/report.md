# Single public Composition: external baseline

Base revision `9f41604de51ef5d5c1b5dd25eee91223af061900`, clean before adding this test. The independent review found the separately allocated `Runtime` wrapper cannot reuse a host Composition, and exposed Composition currently depends on editor, Scene and rendering implementation. The new test asks an installed outside-repository consumer to instantiate `RuntimeComposition`, use one borrowed facade for product and debug controls, create a real Section, read its receipt, Undo and close; compilation also checks that public includes do not pull interaction, Scene, render or Skia internals. It is a scoped baseline, not a replacement for the real Debug UI, Windows window or dual-surface platform tests.

The real install/configure succeeded and the build failed because `canvas/runtime/runtime_composition.hpp` is not installed. Exact commands, output and toolchain are in `sdk-cpp-composition-red.json`. Separately the three previously shipped external tests ran successfully and incompatible `/MD` was rejected, as recorded in `sdk-cpp-composition-preservation.json`. No product source or frozen authority was changed.

The migration is not complete: existing Windows and Web hosts directly depend on the current Composition's platform/render methods and the internal editor types in its public header. The actual Render surface, preview/canonical presentation identities, threading and lifecycle must be moved behind a bounded platform interface while keeping their existing owner; simply aliasing or renaming Runtime would not fulfill the request. Existing `Runtime` must remain until the real consumers have migrated. Platform input generation reuse has a controlled-reordering observation in the independent review, not a physical Windows/Web reproduction; it is not repaired or reclassified here. Document/resources and D07 OOM remain separate. No real window, Chrome or physical input was run in this result.
