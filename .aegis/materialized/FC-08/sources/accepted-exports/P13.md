## 1. 为什么采用两个新增操作，而不是固定原来的四个

已有 InsertObjects、DeleteObjects、RestoreObjects、SetPlacements、SetTransforms、PatchProperties 继续保留已接受语义。安全 Remove Section 不能直接调用旧 DeleteObjects，因为后者依旧是破坏性 subtree/reference closure。

v0.1 的 WrapInSection/RemoveSection 是 Section-only，遗漏 Group/Ungroup；非空 Wrap 不能恢复空容器；同父假设不能覆盖跨 Section 选择。本版把同一领域的“引入包装容器 / 释放包装容器 / 原子重设父级”纳入一个封闭的拓扑操作，其写入范围严格限定如下。

| 操作 | 允许写入 | 明确禁止 |
| --- | --- | --- |
| SetSectionContent | 现存 Section 的完整 SectionContent，支持有界多目标 batch | 更换 kind、改成员、改 Transform、改 RichText/Brush/资源 |
| EditContainerTopology | 新增/恢复或非破坏性移除 Group/Section；现存根的 Placement+Transform；受影响兄弟的 OrderKey | 任意 leaf 的创建或删除；内容/样式/资源修改；嵌套任意 Operation；通用 JSON Patch；“执行后再补偿”伪原子 |

EditContainerTopology 只有三个互斥 effect：IntroduceWrappers、ReleaseWrappers、RelocateObjects。一次操作只选其中一个，禁止同一 payload 同时随意新建和删除任意对象。真正删除 leaf/subtree 仍由旧 DeleteObjects 管理。Group 和 Section 的区别由 kind/capability 与产品命令表达，不能把两种 ObjectKind 合并。

## 2. 共享数据模型与 canonical 集合规则

以下是 reference payload 模型，不是已经落地的 C++ ABI。字段名/局部 tag 均需随 P12/P13 Authority materialization 生成正式 IDL。

```txt
StructuralExpectation {
  object_id, kind_id, kind_version,
  placement_before, transform_before
}
ChildrenExpectation {
  parent_id: optional ObjectId,          // absent = document root
  complete_members: [{object_id, order_key}]
}
TopologyGuard {
  nodes: [StructuralExpectation],
  child_sets: [ChildrenExpectation]
}
Relocation {
  object_id,
  placement_after,
  transform_after
}
OrderOnlyEdit {
  object_id,
  order_key_after
}
EditContainerTopology {
  guard,
  relocations,
  order_only_edits,
  effect: oneof {
    IntroduceWrappers { containers: [ObjectRecord] },
    ReleaseWrappers   { containers_before: [ObjectRecord] },
    RelocateObjects     {}
  }
}
SetSectionContent {
  items: [{object_id, expected_kind_version,
           expected_content, replacement_content}],
  geometry_basis: [StructuralExpectation]
}
```

不存在 <code>isUndo</code>、HistoryId、selectedRoots、pointer/viewport 或 Editor revision 的 wire 字段。expected 前态是 canonical 值的条件，不是另一份持续保存的成员数据库；操作结束后 Document 成员真相仍只有 Placement。

所有以 ObjectId 为键的数组按 unsigned 16-byte ID 升序规范化，重复 key 拒绝，不能 last-write-wins。child\_sets 以 parent 标识为键，root 在对象父 ID 之前；每个 complete\_members 按 child ObjectId 规范化，顺序字段 order\_key 保留为值，不按数组出现顺序决定绘制顺序。TopologyGuard nodes 与删除容器完整 preimage 重叠时必须一致，否则拒绝。

Introduced containers 和 released containers 均要求非空；RelocateObjects 要求 relocations 非空；SetSectionContent.items 非空。其余辅助数组可为空。<b>空容器对应的 complete\_members / relocations 允许为空</b>：这是新操作的明确 collection profile，不更改旧操作的非空规则。创建/移除一个空容器是真实变更，不是空 Operation。无实际字段变化的用户命令在构造阶段返回 NoChange，不添加 History。

新对象 ID 必须有效、当前不存在、互不冲突。恢复原 Group/Section ID 继续采用已接受 absent-ID 加 staged validity 的原则，不新增 tombstone/History-proof 作为 canonical ObjectId 合法性条件。

## 3. Guard、并发检查与原子提交

### 3.1 精确 read-set

每个 relocation 和 order\_only\_edit 的目标都必须有 StructuralExpectation。所有实际使用的旧/新祖先路径，包括最终目标父节点的结构值，必须在 guard.nodes 中完整覆盖；新引入的父容器由 payload 内完整记录覆盖。

每个成员或顺序被改变的旧父、目标父，以及每个被移除的容器，都需要 complete\_children expectation（已有父节点才需要旧值）。它与当前完整直接孩子集合精确相等；不能只检查“用户列出的孩子还存在”，遗漏后来加入的成员。root 的直接孩子集合使用相同语义。

ReleaseWrappers 对每个待移除容器另带完整规范 ObjectRecord preimage，避免移除前别人修改标题/属性而被旧 Undo 静默抹掉。迁移 leaf 不复制其全部 Stroke/Image/RichText 内容到 guard；只改变 Placement/Transform，不覆盖内容。其内部新增后代不会被当成可删除对象。

SetSectionContent 使用 expected\_content 防止整值替换覆盖并发 title/boundary 修改。boundary 改动还必须携带 Section 及完整祖先路径的 geometry\_basis，阻止拖动过程中坐标系变化后套用旧屏幕计算；纯 title/padding/header 修改不要求无关祖先的几何基线。所有语义比较是规范值精确相等，不是 epsilon。

### 3.2 Apply 次序

1. 版本/能力、wire 预算、presence、oneof、集合及值结构检查；规范化得到同一 canonical payload。
2. <b>先做 OperationId 幂等判断，再做依赖当前前态的 guards</b>：相同 ID+相同规范 payload 返回 AlreadyApplied，不产生第二次 mutation/history；同 ID 不同 payload 返回 collision。
3. 在一个 coherent canonical read 上验证 guards、完整成员集合、已有/缺失身份；构造完整 staged resulting graph，校验能力、无环、排序唯一、引用及值合法性。
4. 在唯一 canonical writer 的提交边界绑定 prepared plan。若内部 read generation 已过期，只能丢弃旧 plan，使用同一个 payload 和同一组 guards 重新验证/prepare；不得重算成新的父级、接受新成员或改写 desired values。这不是自动语义 rebase。
5. 预先准备可失败的分配。对本合同承诺可撤销的用户命令，先完成 §3.3 的正向／逆向完整预算准入、逆操作适用性检查及本地 History 存储预留；仅保存 preimage 不构成准入。所有准备及提交基线绑定成功后，才一次发布 canonical 变更、索引更新、generation、幂等结果及 ChangeSet。读者只能观察完整 before 或完整 after。无 Editor History 的 headless replay 不增加这项本地命令准入条件。
6. 提交成功后发布一次命令 receipt、History unit 和 Scene invalidation。Scene 后处理失败须进入既有 projection recovery，不得把已经提交的操作回报成“Rejected 且零变更”，也不得再提交一次相同意图。

任一 commit 前失败：Document、索引、canonical generation、History、commit event 不变。需要重新获取当前场景的命令返回 Stale/Conflict，不自作主张覆盖。已提交操作的网络重试使用同一 OperationId；新的 Undo/Redo 使用新 OperationId。

这里是 semantic 原子发布合同，不声称新增 G7 数据库崩溃恢复或 G8 全局排序协议。持久化与同步继续使用既有 owner 合同。

### 3.3 E01 — 可撤销命令的双向预算准入（CR-02-B01）

本条仅补充 Command/History 提交准入，不新增 Operation、wire 字段、协议版本或硬限制。适用于 §9 中由 FC-08 提供并承诺一个 History unit 的用户命令，包括两个新操作及复用现有 InsertObjects、SetTransforms、PatchProperties、DeleteObjects 等操作的路径；不得换一个正向入口绕过逆向预算检查。不追溯改写既有 Gate 或实现授权包。

<b>UB-01 — 同一基线、真实逆操作。</b> 在一个 coherent canonical 前态 S 上准备正向 F，得到尚未发布的预期后态 S1。按 §10 的精确 preimage/postimage，构造真正可执行的逆操作 U：U 的 guards 来自 S1，而不是照抄 S 的 guards。检查 U 在 S1 上满足结构、引用、身份、完整成员和操作适用性，并恢复本次实际触及的 canonical 字段与对象生命周期；不能只保存“以后再生成 Undo”的占位记录，也不实际向 Document 试执行 U。

```txt
PrepareUndoable(S, F):
  planF, S1 = prepare_without_publication(S, F)
  U = construct_exact_inverse(S, S1, F)
  require inverse_is_applicable(S1, U)
  require inverse_restores_touched_state(S, S1, U)
  require BudgetOK(F) and BudgetOK(U)
  reservation = reserve_local_history_for_pair(F, U, exact_images)
  require reservation succeeds
  bind planF, U, reservation to the same commit basis
  publish F only after all requirements succeed
```

<b>UB-02 — 完整计量，不按选中数量估算。</b> F、U 分别使用最终规范化表示，按各自完整 Operation envelope 的准确编码长度和集合 profile 校验；可以使用与 canonical writer 相同规则的无分配计数遍历，但必须精确计入 tags、length prefixes、所有 envelope 字段及实际 payload。尚未分配的 Undo OperationId 按既有固定 16-byte 非零 ID 载体计量，执行时仍正常分配新 ID 并做通常校验。每个方向都要计入 StructuralExpectation、完整 ChildrenExpectation、wrapper 完整记录／恢复记录、relocations、OrderOnlyEdit、expected/replacement content 和适用祖先依赖；不能省略重复出现在不同字段中的实际编码开销。嵌套集合逐个及需要聚合的计数均遵循其 profile，checked arithmetic 溢出即失败。

沿用 P12 §3.2 与既有安全预算：每个适用 keyed batch 最多 65,535 项，单个编码 Operation 最多 33,554,432 bytes，及 ObjectRecord、字符串、OrderKey、几何等适用限制。F 与 U 各自满足单操作限额，不把二者合并误算为一条 wire Operation；本地 History 的合计存储成本另行计量。该检查不是新增 Document 总对象数上限。

<b>UB-03 — 在发布前预留 History。</b> 必须在正向发布前准备本次 History unit 所需的确切记录或等价有界物化存储，包含保留的正反向值、逆向 guards、preimage/postimage 和重做所需信息，避免已提交后才因创建本次记录失败而静默失去撤销能力。预留与 prepared plan 绑定；拒绝或取消时释放临时资源，不移动 History cursor、不清空 redo 分支，也不先丢弃现有 History 再返回失败。既有容量保留策略若涉及旧记录回收，只能在成功发布的既有策略边界执行。本条不规定新的数据库事务、持久化恢复协议或无限期保留策略。

<b>UB-04 — 准入与实际提交不能脱节。</b> 若 prepared-plan 基线过期，按 §3.2 使用同一 F 和既定 guards 重新验证；同时使旧准入结果失效，并对重新准备的真实 S/S1、逆操作和预留重新核对。不能把旧预算结论用于已变化的计划，也不能借重验吸纳新增成员或自动 rebase 旧用户意图。需要新意图时返回明确 Stale/Conflict。

<b>UB-05 — 不通过就零提交。</b> 任一方向超限、无法构造合法逆操作或无法预留本地 History 时，正向不得发布。沿用 BudgetExceeded，并给出 forward/inverse/history-reservation 的本地原因；逆语义不合法则使用已有适用错误／HistoryConflict。Document、索引、canonical generation、History cursor、redo 分支和 commit event 均不变。禁止截断 guards、拆分同一原子意图、扩大协议预算、改成破坏性删除，或提交后把命令降级为不可撤销。

<b>UB-06 — canonical/replay 边界不变。</b> 这是提供可撤销用户命令的本地准入规则，不把 Editor History 是否存在、本地 History 容量或预留 token 变成 canonical payload／Operation 合法性条件。普通 headless replay、既有远程和导入路径仍按各自已接受契约执行；只有它们明确承诺生成本地可撤销命令时才适用该准入。AlreadyApplied 仍先于依赖状态的 guards，不重复分配 History unit。后续 P20 验证这条合同，不负责发明新的限额。

## 4. IntroduceWrappers：Group、Section、空容器和恢复

仅允许引入合法 Group 或 Section 完整记录，目标 ID 当前必须不存在。新容器可形成有界无环森林：允许 Group→Section、Section→Group、Section→Section；合法的新父可位于同一 payload 中。

所有现存 relocation 对象仍保留 ObjectId/kind/content/properties，仅原子替换 Placement+Transform。此 effect 下它们的新直接父必须属于新容器集合；不能顺便搬走不参与包装的其他对象。普通 GroupSelected/WrapInSection 的选区输入根不得互为祖孙；但 canonical relocation 集合不是 SelectionState，恢复被分隔的多层容器时允许存在必要的祖孙依赖。每个 ObjectId 只赋一次绝对 after 值，在同一 staged final graph 中解析，不向后代重复施加祖先 delta。新容器本身的 Placement 描述其内部嵌套，不重复放进 relocation。

每个 introduced wrapper 允许零个孩子。因此创建空 Section、恢复空 Section、恢复空 Group 均有同一合法生命周期表示。UI 的“Wrap 选区”仍要求实际有选中对象；空选区不是让 canonical core 拒绝空容器的理由。

普通 GroupSelected/WrapInSection 创建一个 wrapper；恢复一次同时释放的嵌套容器可创建完整 wrapper forest。相同 effect 只引入 Group/Section，不是可插入任意 leaf 的通用批量事务。

所有 created wrappers 和现存 relocation 后态同时 stage。任何 unsupported child、cycle、ID 冲突或非法 OrderKey 导致全操作拒绝。产品侧结果选择新包装根，但该 Selection 更新是提交成功后的 local projection，不进入 canonical payload，headless replay 不修改 Selection。

## 5. ReleaseWrappers：Ungroup 与安全 Remove Section

ReleaseWrappers 非破坏性删除指定 Group/Section 节点，<b>不调用原 DeleteObjects 的 subtree cascade</b>。删前完整记录必须与 containers\_before 一致。

定义存活边界根：

```txt
R = 要移除的 Group/Section IDs
frontier = { o | o 不在 R，且 before.parent(o) 在 R }
```

relocations 必须精确覆盖 frontier：每个 ID 一次，不能漏掉直接孩子，不能把整个后代集合都重复列入。若某个待移除容器是另一待移除容器的孩子，它在 R 中被删除，不作为存活 frontier 重设父级。所有保留的子树内部关系不变。

<b>普通 Ungroup/Remove 命令：</b> frontier 的目标是沿其旧父链向上遇到的第一个未被移除的父节点，或 root；保留各子树的 world pose。多个 Group/Section 可在同一次显式非破坏性解包命令中处理，包含嵌套移除集合。

<b>Undo-Wrap 的同一 canonical effect：</b> relocation 的目标可以是分别保存的原父节点，而不被强制提升到 wrapper 原父级。canonical effect 明确表示“移除指定包装节点，并把全部存活 frontier 放到 payload 指定的合法父级”；它不读取 Editor History 来猜目标。普通安全移除与 Undo 的不同路由由各自命令构造，最终都是有完整 guards 的绝对值 payload。

空 Section/Group 对应空 frontier，容器删除仍原子、有效、可撤销。不存在新 attach target 的容器引用；如未来版本出现本合同未接受的依赖引用，拒绝或先进行独立 Authority 扩展，不隐式 detach/delete。

## 6. RelocateObjects：原子重设父级与拖放提交

要求现存变更目标非空且 ObjectId 唯一，全部 target 及相关 parent/ancestor guards 完整。普通交互命令仍只接收合法的无祖孙重复 Selection roots；canonical relocation 是精确结构变更集，允许 Undo/批次恢复所必需的祖孙依赖。每个目标只写一次绝对后态，在完整 final graph 上校验，不能依输入顺序累加祖先 delta。Placement 的 parent\_id 与 order\_key 仍作为一个原子值；加上 transform\_after 一并提交，不改变旧 SetPlacements 的 payload。

最终 parent 可为合法现存父，且最终图必须无环。多个 relocation 同时验证最终图，不能依赖 item 遍历顺序。

纯 Reparent 命令用旧 world pose 作为 desired W；拖放包含用户显式移动时，用 pointer session 最终 preview world pose 作为 desired W，并在同一个拓扑操作内完成 drop 重设父级。所谓“保持姿态”指不因坐标系更换而从最终 preview 跳位，不是禁止用户先拖动物体。

跨过 Section 几何边界不生成操作；只有明确接受的 drop/命令才提交。Scene、鼠标位置、scope 和平台状态不参与 headless apply；payload 已经带绝对最终值。

## 7. 跨父 Wrap、LCA 与 OrderKey

### 7.1 不再假定 selected roots 是同父兄弟

由原 FC-01A/D06 resolver 得到的合法选中根，可能来自同一 Group 编辑 scope 内的不同 Section。命令保留该选区规则，不把跨父输入改成静默跳过。

默认 Wrap 的目标父选择<b>所有选中根的原 parent 路径的最近合法共同祖先</b>，只能是 root、Group 或 Section，并尊重当前合法 Group 编辑范围。显式 MoveToContainer 使用用户指定且通过能力检查的父。目标不得位于被迁移根的后代中；最终图能力不合法则全失败，不强行扁平化。

普通新 wrapper 的 L 取目标父局部空间的单位矩阵；将选中根的几何和 W 映射到该空间后计算 Section boundary+padding/header。Group 不保存该 derived bounds。使用其他初始 L 的未来 preset 仍必须保证相同 PoseConstruction 结果，不让 apply 依赖 bounds 重新计算。

对每个选中根分别保存原 Placement、Transform、OrderKey。Undo 返回各自原父级，而不是假定一个共同父级。源 Section 被搬空后仍保留为合法空 Section，不自动删除。

### 7.2 排序规则与可承诺的保真范围

兄弟按既有 OrderKey unsigned-byte lexicographic 顺序排列，不用 ObjectId 数值替代绘制层次。跨父输入的相对次序由 before canonical ancestor OrderKey 路径确定。

Wrap 将新 wrapper 放在目标父中被选根所覆盖的最靠前分支位置之后、下一个未受影响兄弟之前；新 wrapper 内按所选根原 canonical 相对顺序排列。同父的情况是该规则的特例。

普通 Release 按各被移除 wrapper 的原 slot 展开 frontier；遇到连续移除的嵌套 wrapper 时按原层级顺序展开，遇到存活子树保持其根作为一个单位。Undo 则恢复保存的确切旧 keys 和 parents。

必须诚实区分：坐标/几何保持与任意全局遮挡顺序保持不是同一承诺。把不连续跨父对象变成一个真实容器可能改变其与非成员的交错；本版保证成员相对顺序和非成员之间的相对顺序，定义新容器 slot，不宣称所有外部 interleaving 都不变。

OrderKey 由命令方产生并显式写入，replay 不再分配。若目标间隙不够，可在同一操作的 order\_only\_edits 内重新编号受影响的现存兄弟；必须有 before guards、原 parent 不变、Transform/content 不变、未参与对象的相对次序不变。relocation 与 order\_only\_edits ID 交集禁止。超过现行 key/batch/byte 预算时完整拒绝，不分批破坏原子性。

## 8. 数值、姿态保持与唯一语义来源

使用配对 P12 §6 的 PoseConstruction/1。操作存储绝对 transform\_after；其接受不依赖平台 renderer、当前字体、显示缩放或一个由 P20 自定的 world-pose epsilon。canonical equality 和 guards 精确匹配。

命令构造必须先用 coherent before read 得到 desired W，再按最终 parent W 计算 L\_after，执行已定义质量检查，最后提交唯一绝对结果。需要无损撤销的字段恢复使用已保存 preimage，不把重新求逆的近似值当作旧值。

Group/Section 根变换使用既有 SetTransforms，只改根一次。这里不许可对同一个意图同时改祖先矩阵和其后代矩阵，除非是本拓扑命令所必需且明确表达的重设父级。隐藏成员的结构变换不能因当前 viewport 不可见而遗漏。

| 创建空 Section | InsertObjects 或本领域 IntroduceWrappers；生产入口选定一种，不重复提交 | ReleaseWrappers，仅删除该空容器 |
| GroupSelected / WrapInSection | EditContainerTopology.IntroduceWrappers | ReleaseWrappers + 每个成员原父级/姿态/顺序 |
| Ungroup / Remove Section | EditContainerTopology.ReleaseWrappers | IntroduceWrappers 恢复所有旧容器完整记录 + frontier 原值 |
| 空容器 Remove / Undo | ReleaseWrappers，空 frontier | IntroduceWrappers，空 adoptions；原 ObjectId 保留 |
| 跨父 reparent / 明确 drop | EditContainerTopology.RelocateObjects | 同 variant + exact before Placement/Transform/OrderKey |
| 多个 Group/Section 的显式非破坏性解包 | 一个 ReleaseWrappers batch，完整 frontier | 一个 IntroduceWrappers batch，可恢复嵌套森林 |
| Group move/rotate/scale；Section move | 既有 SetTransforms，选中根去重 | 既有 inverse SetTransforms，保存根前态 |
| Section 边界 resize / rename / padding / header | SetSectionContent，expected\_content+replacement | SetSectionContent 恢复完整前态 |
| Section 背景/自身 opacity | 既有 PatchProperties 的 accepted Section applicability | 既有属性 preimage/Clear 规则 |
| Delete Group；Delete Section and Contents | 既有 DeleteObjects，完整 subtree+Connector closure | 既有 RestoreObjects 完整删除 preimage |

<b>通用 Delete 的多选集成边界：</b> 单 Section/全部 Section 的默认 Delete 是安全 Release；Group 的普通 Delete 仍破坏性，不自动变成 Ungroup。若一个多选命令混合 Section-safe-release 与普通对象/Group 的 destructive-delete，本版两个新领域操作不能假装组成一个 canonical 原子步骤。命令聚合层必须在开始前返回明确的 UnsupportedMixedRemoval/需要显式动作，而不能先执行一半，也不能将安全默认改成破坏性删除。需要一个按钮原子混合两种删除语义时，必须由 FC-04/FC-10 的明确后续合同承接；这不是本轮新获产品批准的功能缩减，也不是宣称该集成能力已完成。显式混合 Group/Section 非破坏性解包和纯破坏性 DeleteObjects 批次均已完整建模。

## 10. History 的精确正反向合同

一次成功命令只增加一个 History unit。包含 forward canonical payload、精确 touched-field preimage/postimage、被创建/移除 wrapper 的完整记录、旧新兄弟顺序，以及生成逆操作所需的结构依赖；不复制无关整个 Document。

Introduce↔Release 是<b>有完整条件的状态变更对</b>，不是只有按钮名称的互逆假设。逆 payload 针对 forward poststate 构造 guards；应用逆操作仍经过正常 codec、state validation 和单次 atomic apply。

Undo-Wrap 必须验证 wrapper 本身、它的完整直接成员集合、原目标父和当前父路径、相关次序未发生冲突。若后来加入新直接成员，不能把它也一起撤销；返回 HistoryConflict，保持文档与 History cursor 不变。若目标原父已删除或身份已被别的对象占用，同样拒绝，不找一个近似替代父。

特别检查非相邻嵌套解包：<code>A(移除) → B(保留) → C(移除) → D(保留)</code>。Release 的 frontier 为 B、D，二者可能仍有祖孙依赖；逆 Introduce 同时恢复 A、C，并分别恢复 B、D 的原 Placement/Transform。它们不是被用户重复选中的两个独立变换根，因此不能以 Selection antichain 条件拒绝合法逆操作；也不能逐项执行祖先 delta。另一个例子是原兄弟 A、B 的批次 relocation 使 A 成为 B 的子节点，逆 relocation 仍须能恢复原兄弟关系。这两个方向都用完整 guards 和绝对 final graph 校验。

被保留的现存 leaf 内容若变化但本逆操作不覆盖其内容，不通过整对象旧快照把新内容覆盖回去；被删除 wrapper 的元数据必须匹配 forward 后态，以避免意外抹除新 title/style。无关文档对象修改不需要因一个全局 revision 不同就伪判 canonical 冲突；内部 prepared-plan generation 仅用于并发安全。

Undo/Redo 新建 OperationId，但恢复相同 ObjectId 与 exact canonical 字段。重复投递一个已执行 ID 不移动 History cursor 两次。空容器也适用此规则，没有“必须先伪造一个孩子”的特殊分支。

DeleteObjects/RestoreObjects 的既有语义不改；History 必须保存已解析的完整删除闭包。Redo 在当前依赖已变化时不能扩大删除集去吸纳新对象。资源恢复、权限与协作冲突依旧遵守各自 owner，不能以 History 为名绕过安全检查。

### 10.1 E01 — Undo/Redo 的预算闭包与承诺边界

UB-01～06 是本节的强制前提。没有相关外部状态变化、使用同一协议 profile 且本条 History 记录仍保留时，已经准入并提交的 F 必须有在其预期后态 S1 中可提交的真实 U；不能因提交当时即可计算出的集合或编码超限而丧失 Undo。

Redo 使用保存的精确正向字段／结果和新的 OperationId；Undo、Redo 每次执行前都检查当前 guards、实际待提交方向及其反向方向的预算和本地准备。无冲突的 S 与 S1 往返只需检查同一有限状态对，不递归生成无限层“逆操作的逆操作”，也不要求额外的 proof-of-proof。幂等账本和 generation 按新操作正常推进；精确恢复指 touched canonical 文档状态，不是回滚这些单调执行元数据。

后续成员、祖先、标题或相关排序变化仍按现有合同返回 HistoryConflict；不能用原先的预算准入授权覆盖新状态，也不能重算更大的删除闭包。保留的 leaf 内容变化不得被整对象旧快照覆盖。该承诺不是任意并发下无条件 Undo，也不是对未来内存耗尽、进程崩溃、History 正常淘汰或能力降级的可用性保证；这些情况不得误报成功或部分执行。

准入对空／非空 Group 和 Section、跨父 Wrap、嵌套 Release/Restore、relabel、内容修改以及本合同中的复用旧操作路径一视同仁。尤其 DeleteObjects 的短 ID 列表必须与实际 RestoreObjects 完整删除闭包的逆向大小分别检查，不能把“小正向”等同于“小 Undo”。本节不更改旧 DeleteObjects/RestoreObjects 的 wire 语义，也不替 INT-01 创造隐含事务。

## 11. 错误与结果状态（逻辑名称，非最终错误码分配）

UnsupportedFeature/UnsupportedVersion、MalformedPayload、InvalidApplicability、MissingTarget、IdentityCollision、Cycle、OrderKeyCollision、StalePrecondition、MembershipChanged、NumericRange、BudgetExceeded、HistoryConflict 均在 commit 前拒绝；不得 success-with-partial-mutation。

AlreadyApplied 只表示同 OperationId 相同规范 payload 已执行；NoChange 是未提交用户命令的结果，不制造空操作；CommittedPendingProjection 不能被后续 Scene failure 改称未提交。最终数值 error code、stage/path golden 随后由对应 Authority/verification 绑定，逻辑类别和零变更边界由本 P13 先定义。

## 12. 版本、能力及 legacy 保留

按 P12 的候选分配：SetSectionContent kind/tag17、EditContainerTopology kind/tag18；新操作 schema\_version=1/payload\_version=1，未知 effect 拒绝。1～16 所有已接受 identity 和 payload 语义不重写，UpdateResourceManifest=16 不是空槽。

EditContainerTopology 要求 container-topology-v1，即使只处理 Group。任一 Section record/target 还要求 section-v1 及已接受 hierarchy successor。SetSectionContent 要求 section-v1。全部能力检查发生在修改前，不把“读得懂 Group-only snapshot”当作能 replay 新 topology op。

三个 effect 的 nested collections 有单独 presence/empty/key profile；外层历史 canonical writer 的数字、ID、大小限制继续复用。新版 writer 不生成旧客户端无法理解却标作无能力要求的操作流。Snapshot 的状态能力与后续 journal 操作能力按 P12 分开，不凭空增加 Editor transaction/session 字段。

## 13. 有限 domain 与最小性说明

本版从四个 Section-only opcode 收敛为两个候选 opcode，但不是以数量少为目标。SetSectionContent 是一个 kind-specific 内容 mutation；EditContainerTopology 是一个固定写入域、固定三个 effect、单一 staged graph 的领域 mutation。与已有 RichTextDelta 的领域内步骤类似，它不恢复一个包裹任意 canonical operations 的全局 Transaction。

新增任意 leaf create/delete、样式/text/asset 编辑、混合安全/破坏性 deletion 或其他容器种类都不能经未声明字段塞进该操作；必须独立评估能力和版本。未来是否拆成独立 opcode 是 wire/演进选择，不能改变已经定义的 all-or-nothing、History 和 payload 确定性要求。
