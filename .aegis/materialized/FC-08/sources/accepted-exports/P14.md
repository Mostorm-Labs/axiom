## 1. 架构选择

本版选择：<b>复用现有 Composition、Interaction、Semantic、Scene 与 History owner，在其中增加受限容器模块。</b> 不新增并列 ContainerRuntime 或容器文档。

替代方案一：Shell/ImGui 分别管理成员和拼装操作。虽易做出 UI，但产生多份归属、原子性和取消规则，违反现有公共 Facade 边界，排除。

替代方案二：把容器生命周期全部放入 Renderer/Scene，依据重叠推断成员。不能满足 canonical reparent、Undo、headless replay，排除。

替代方案三：另建 ContainerRuntime、History 和命令队列。虽隔离局部代码，却重复文档生命周期、提交顺序和恢复状态；本功能没有需要第二个运行时的依据，排除。下述模块名是候选逻辑边界，不要求每个边界单独新建库。

```txt
Product Shell / Debug UI / ordinary consumer
    -> typed RuntimeFacade intent + immutable readback
    -> Composition owner admission / ordered control lane
    -> Interaction command planner + existing EditorHistory/E01
    -> Semantic OperationEngine prepare / atomic apply
    -> CanonicalCommitRecord + ChangeSet
    -> existing Scene coordinator -> coherent Scene/Bounds/Spatial publication
    -> RenderView / common overlays -> platform surface

Platform pointer facts -> existing InputRouter / arbiter
    -> container gesture session -> transient preview
    -> final confirmed intent joins the SAME owner commit lane
```

## 2. 单一所有权表

| 状态或责任 | 唯一 owner | 禁止拥有的第二真相 |
| --- | --- | --- |
| ObjectId、Placement、SectionContent、Transform、适用属性 | Semantic Document/Store，由 OperationEngine 写入 | UI members 数组、Scene 反写 parent、平台矩阵 |
| 已提交 canonical 顺序、幂等、generation | 现有 semantic writer / commit clock | 每个容器一个 writer 或网络自造顺序 |
| 命令请求、CanvasTargetKey、owner 调度和 receipt | RuntimeComposition / CanvasRuntimeFacade | Debug command 私有执行通道 |
| 选区、Group scope、工具和 gesture | Interaction / 每个 EditorSession-view | canonical selection、Section 新编辑 scope |
| Wrap/LCA/OrderKey/PoseConstruction、精确前后态计划 | Interaction 的 ContainerCommandPlanner | JS、ImGui、Renderer 内拼装 canonical payload |
| 可撤销命令 F/U 准入与本地 History 记录 | 同一 EditorHistory 及其命令协调边界 | Semantic apply 依赖本地 History 容量 |
| 祖先变换、derived world bounds、索引和绘制顺序 | Scene，来源是同一 canonical read/ChangeSet | 第二份可编辑层级或新 SpatialIndex |
| 字形与标题布局 | 共用 Text layout/render 服务 | DOM/Win32 字宽改变 canonical boundary |
| 本机 capture、坐标事实、IME widget、实际 present | Platform Host | Host 选择算法、Undo、成员管理 |
| checkpoint/journal/blob 的耐久性 | 既有 persistence/recovery owner | 将 Applied receipt 当作已落盘／已同步 |

## 3. 运行时、线程和身份边界

一个 mounted Document 的 canonical mutation 只在现有 owner lane 线性化。多个视图共享该文档时，各自保留 Camera、selection、preview；View A 的选择不能替换 View B 的本地选择。新模块由 Composition 构造、注入既有 ports 并销毁，不向调用者泄漏 mutable store。

沿用完整 <code>CanvasTargetKey(runtimeEpoch, viewId, viewEpoch, attachmentEpoch)</code>；DocumentId 由 mount binding 关联，不在 target 中偷偷扩充 wire。请求使用 clientId/requestId；活动输入使用完整 PointerKey。SemanticGeneration、SceneRevision、camera/metrics revision、requestId 和 OperationId 不能互换。

Facade 的异线程调用只复制/排队拥有的 typed 值；读取返回拥有寿命的不可变快照。现有 span 型 SceneReadView 不得跨 owner pump、跨线程或跨重新挂载长期保存。新工作引用的旧快照必须拥有稳定存储或在同一 owner 步骤内消费。

首版不要求 worker 构建 canonical payload；有限工作在 owner 内完成。若未来切到 worker，worker 只接收不可变输入并返回建议计划，owner 必须重新验证 guards；不得在 worker 直接 apply。

## 4. 两个发布边界，不能伪装成一个事务

<b>canonical 边界：</b> 验证、资源准备、精确 F/U 与 E01 History 预留通过后，一次发布文档、索引、幂等结果、generation 和 commit record。准备失败无 canonical 写入，History cursor 不动。

<b>projection 边界：</b> 既有 IncrementalRuntimeCoordinator/SceneBinding 依据该提交准备 RuntimeScene、Bounds、Spatial、damage，并发布一致版本。不能先公开新 Bounds、再公开旧 RenderScene。这里的 Scene publication transaction 只是派生状态一致性，不是包裹多个 canonical Operation 的新 Transaction。

canonical 成功后投影失败，返回 <code>CommittedPendingProjection</code> 并进入既有 recovery；History 仍记录该成功意图。不能对用户报告 Rejected/零变更，不能重放同一意图修补画面。几何依赖命令在投影落后时以 Busy/ProjectionUnavailable 拒绝或等待；无几何依赖的命令仍按既有 lifecycle 与 read-set 准入。

预留的本地 History、终态 receipt 和提交元数据在 canonical 发布后不能依赖新的可失败分配。进程崩溃后的本地 History 恢复不是本轮 durability 承诺。

## 5. 三类 bounds 与非裁剪层级

Section 的独立 boundary 不是所有用途共用的一只 AABB。本版明确区分：

| 派生几何 | 用途 | 不允许替代 |
| --- | --- | --- |
| own boundary quad / local Rect2 | Section 边界手柄、full-containment、空白背景命中 | 不作为所有后代可见性范围 |
| own paint bounds | 背景和标题实际绘制、该对象自身 damage | 不等于内部对象命中区域 |
| subtree visual union | 子树 culling、安全的 subtree damage、内容范围查询 | 不替代 Group 的精确 descendant hit，不改变 Section full-containment |

Group 无独立 painted rectangle，聚合几何来自实际 descendants。Section 后代可以在边界外：viewport 与 Section 外框不相交时，仍须查询和绘制相交的后代。Section opacity 只影响自身，不乘到后代；不创建 clip/opacity render group。

Section 内的绘制沿 canonical hierarchy/OrderKey 和既有排序契约；背景不能成为覆盖孩子的后置 opaque 层。所有辅助线和选中 chrome 位于共用 transient overlay，不写 ObjectContent。

## 6. 选择、变化传播和资源失效

点击先使用实际对象几何，再按已接受 Group root-first/scope 解析；Section 背景不能吞掉孩子。完整 region containment 用 transformed boundary 的 exact geometry，AABB 仅用于 broad phase。Section 被作为根选择时后代去重；部分覆盖继续查询孩子。Shift/取消/hidden-locked 策略继承既有 owner，不在平台实现一套特例。

根 Transform 改动使全部后代 world pose 派生失效，不能因 ChangeSet 只含根 ObjectId 就漏掉子树；子对象变化需向上更新 Group/subtree union。reparent 同时失效旧、新祖先路径；损伤至少覆盖 old/new visual union。对 attached Connector 和受影响路由走既有依赖索引与路由 owner，不给 Section/Group 新 attachment 资格。

boundary resize 只改 SectionContent：后代 Transform、成员归属、RichText wrapping/图片裁剪不变；标题布局与自身 bounds 可变化。字体到达只刷新派生标题，不写 operation/history/generation。所有这些增量通过现有 coordinator，不另造投影队列。

- [OperationEngine](https://github.com/Mostorm-Labs/axiom/blob/e5e630c5662167763fc7ba66b94c35881b1e1470/runtime/semantic/include/canvas/semantic/operation_engine.hpp) 与 [PreparedApplyPlan](https://github.com/Mostorm-Labs/axiom/blob/e5e630c5662167763fc7ba66b94c35881b1e1470/runtime/semantic/include/canvas/semantic/apply_plan.hpp)：可复用 prepare/apply owner；尚不能据此宣称 opcode17/18、E01 或 owner-bound prepared commit 已实现。
- [EditorHistory](https://github.com/Mostorm-Labs/axiom/blob/e5e630c5662167763fc7ba66b94c35881b1e1470/runtime/interaction/include/canvas/interaction/editor_history.hpp)：已有 prepareRecord/commitPrepared 与 conditional submit；需要接入真实逆操作预算和容器前后态。
- [IncrementalRuntimeCoordinator](https://github.com/Mostorm-Labs/axiom/blob/e5e630c5662167763fc7ba66b94c35881b1e1470/runtime/scene/include/canvas/scene/incremental_runtime_coordinator.hpp) 与 [Scene](https://github.com/Mostorm-Labs/axiom/blob/e5e630c5662167763fc7ba66b94c35881b1e1470/runtime/scene/include/canvas/scene/scene.hpp)：已有 coherent publication/recovery，需新增容器派生数据和失效闭包。

上列是接入位置，不是源码已经满足 FC-08 的断言。BASE-01 的 source-complete descriptor 物化和 capability source drift 仍交对应 owner；不在本架构里承认第二种 wire 格式。
